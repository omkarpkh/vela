# Press feedback

**Decided 23 September 2026. Shipped: a hit-target fix, an asymmetric press, a keyboard
acknowledgement, and the anchored press as a documented enhancement layer. The option that
scored highest shipped nothing but one idea.**

`prototype.html` is ten candidates on one page, each counting its own presses against the clicks
that actually landed. `media/press-comparison.webm` is a recording of it, regenerated by
`tests/media/record-press.spec.ts` — so the clip re-records itself whenever the press changes.

---

## What started it

Vela's button shrinks 3% when pressed. That rule shipped in 0.9.0 and nobody had questioned it: it
is what most design systems do, and it looks right.

Two things made it worth questioning. Apple's WWDC24 session on fluid interfaces criticises exactly
this pattern — *the animation does not respond to where I touch it* — and the geometry has a
consequence nobody in the surveyed systems had written down. A centre-origin scale pulls both edges
inward **while the pointer is still down**: 4.80px a side on a 320px button, 1.5px at 102px. Press
near an edge and the button moves out from under the cursor before the release.

**This is a mouse defect only.** The same gesture as a touch loses nothing — 0/12 against the
mouse's 9/12 — because the browser sets implicit pointer capture on touch and pen, as the Pointer
Events spec requires, and does not for a mouse. `gotpointercapture` fires on every touch run and
never on a mouse one. The JavaScript layer's `setPointerCapture` is therefore not a trick: it gives
the mouse the behaviour touch has always had.

## The measurements

Pressing 2px inside the edge of a 320px-wide button, 40 presses per candidate, box re-measured
before each press:

| | Chromium | WebKit |
|---|---|---|
| Baseline — centre scale, no protection | **40/40 lost** | **35/40 lost** |
| G — Linear's pattern, reproduced | **40/40 lost** | **35/40 lost** |
| A, D, F, H, I — anchored, guarded, or no geometry | 0/40 | 0/40 |

Confirmed on the shipped component too, with the guard toggled and nothing else changed:
10/30 lost without it, 0/30 with it.

Three notes on measuring this, each of which cost a wrong answer first:

1. **Re-read the button's box before every press.** The first press shifts the playground's layout
   by several pixels; a harness that measures once is soon pressing where the button is not, which
   looks exactly like the defect and is not.
2. **Check what the selector actually matched.** `.vela-btn` first matches a theme toggle in the
   playground chrome, not the component.
3. **`setPointerCapture` makes a button immune.** Any harness running against a build that captures
   the pointer will report zero losses regardless of geometry, because the release is delivered to
   the button whatever it did. Removing a class that disables the CSS press path does not disable
   the handlers.

Always run a control that cannot exhibit the effect — pressing 40px inside the button — before
believing any rate.

## Why the winner did not ship, and the runner-up only half did

**I violates the foundation it was built for.** It hardcodes `70ms`, `210ms` and a bespoke curve.
`guidelines/foundations/motion.md`: *"No component defines its own duration or curve. A new one is a
token change, reviewed like a colour."* The Dart and MUI generators both `throw` on a duration that
is not `<n>ms`, so those literals reach exactly one of five targets. The idea was right — motion
rule 2 already requires asymmetry of hover — so it shipped, as a token.

**A cannot be delivered in CSS.** Anchoring needs the pointer position, which means a handler.
Flutter ships tokens and no button. The MUI bridge is JSON and can never carry one. Figma has no
expression for it. That constraint eliminates six of ten candidates, and no weighting dimension
asked about it: in a five-target system, *how many targets does this reach* is a gate before
scoring, not a criterion inside it.

It left two honest positions: withhold the better press so every target behaves identically, or
let each target do the best it can and make the seam explicit. **The second was chosen.** A ships
as an enhancement layer — the pressed pixel moves 0.06px against the centre scale's 4.80px — on
top of a CSS press that is complete without it.

The cost was paid in documentation, which is where it belongs. `guidelines/llms.txt` used to
promise a port "translates only the syntax"; that stopped being true the moment one target could
do more than another. It now states that an enhancement is additive by definition, may not touch
the props, the markup or what the CSS does alone, and that skipping it costs feel and never
function. `button-enhancement-not-load-bearing` is a hard constraint, proved by a browser test
that strips the JS path out and asserts the press is still correct.

Two implementation facts worth keeping. The pivot cannot be handed to a CSS `:active` rule: the
browser paints the scale in the same frame the handler is writing, and when the write loses, the
press pivots on the *previous* contact point — the far edge, the largest error available. So the
component drives the press itself and writes pivot and pressed flag in one statement. And it must
capture the pointer, because otherwise the scale moves the button out from under the pointer and
fires `pointerleave`, ending the press because of the press.

## What the measurement overturned

Every system surveyed pairs the press with a colour change, and the prototype carried a 2%
darkening on that basis. Pressed in a real browser it was invisible — and not because 2% is too
subtle. `filter: brightness()` multiplies everything the element paints, the label included, so
figure and ground dim together and the contrast a person actually reads barely moves: **6.08:1 →
6.00:1 at 2%, and 5.69:1 at 10%, which is worse.** Turning it up cannot make it work.

This does not condemn the light-based options. B, C and E *add* light at a point rather than
scaling everything down, so they create local contrast and they read. Those came out because
motion.md says motion here is feedback, never decoration, and a glow under the cursor of a security
console is decoration.

## What shipped

- **A press no longer moves its own hit target.** A counter-scaled `::after` (0.97 × 1.0309278 = 1)
  holding the original border box for the length of the press. Pure CSS, no handler, so every
  target and every framework port gets it.
- **An asymmetric press** — in at the new `--vela-duration-instant` (70ms, under the ~85ms where
  delay begins to read as lag), out at `--vela-duration-base` (180ms).
- **A keyboard acknowledgement**, borrowed from H, which placed sixth: the focus ring collapses
  onto the edge. A state change with no duration, so *"from the keyboard, nothing animates"* holds,
  and Space and Enter stop being the only inputs with no feedback at all.
- **The anchored press, as a layer that is additive by contract.** `vela-btn--js` switches the
  CSS `:active` path off so the two never both apply; nothing about the props, the markup or the
  accessibility differs between them.
- **A `browser` level in the rule-coverage gate.** The press rule is enforced and provable, but not
  by jsdom (no hit-testing) and not by a screenshot (identical pixels). Filing it as a convention
  would have been the safe direction and also untrue.

A second fix surfaced on the way: capturing the pointer on `pointerdown` solves this as completely
as the guard does, because every later event is delivered to the button whatever the geometry does.
It needs JavaScript, so it rides with the enhancement rather than carrying the contract.

## Found on the way past, and fixed

In dark mode the primary button's hover background was **3.18:1** against its own white label and
the destructive button's was **4.08:1**; AA needs 4.5. Both are states a person sees on the way to
every mouse press. The dark hovers reached for `primary-400` and `red-500`, which are also the
focus ring, link text and severity signals, so those keep their values and two new ramp steps carry
the hover: `primary-450` (#187e91, 4.74:1) and `red-600` (#cd4336, 4.72:1). Both sit in the 4–7 ΔL\*
band where a hover step reads; the old values were overshooting at +18.2 and +13.1 as well as
failing.

The reason it survived is the more useful half: **no hover pair was in `PAIRS`**, so "WCAG AA
asserted in CI" was only ever true of buttons sitting still. Four hover pairs are now asserted
across both themes.

## Still open

- **Three holes in the anchored path**, none of which can lose a click — the guard holds the target
  regardless — but each of which can make the press look wrong for a frame: a stale origin
  outliving its press, a mid-flight re-press snapping the pivot against a running transform, and a
  rotated ancestor making the bounding box the wrong shape.
